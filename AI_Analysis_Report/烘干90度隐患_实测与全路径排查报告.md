## 0. 一句话结论

**设定值真的是 750 时，烘干通道在数学上不可能让读数到 90℃，因为保护阈值和显示值是同一个变量。**

## 2. 控制律反推：模型与实测逐位吻合

烘干通道（`TaskTempModule.c:249-281`）：

```
dev   = (Temset - Temin) / 10            // 单位 ℃
fout  = Kp*dev + Ki*dev_sum + Kd*(dev_last-dev) + 5      // piheat_pid.c:100
wPwm  = (int)fout * 2                    // TaskTempModule.c:249
wPwm  = clamp(wPwm, 0, 100)              // :250-251
```

实参 `Kp=20, Ki=0, Kd=0`（`TaskTempModule.c:483-485`），代入得：

```
wPwm = 2 × (20×ΔT + 5) = 40×ΔT + 10      （ΔT = 设定 − 实测，单位 ℃）
```

**用实测验算**：`Tset=750`、`Temin=748` → ΔT = 0.2℃ → `40×0.2+10 = 18`。
实测 `wPwm = 18`。**逐位吻合，模型可信。**

推论：
- 占空比在 **ΔT ≥ 2.25℃ 即饱和 100%**。
- ΔT = 0 时仍有 **10% 的底值**。
- 稳态需要约 18% 才能维持 75℃，所以平衡点是 `40ΔT+10 = 18 → ΔT = 0.2`，即 **74.8℃** —— 与实测均值 74.78℃ 完全一致。`Ki=0` 带来的 0.2℃ 稳态误差是可预测的，不是故障。

## 3. 保护逻辑的完整结构（决定 90℃ 是否可能）

烘干任务每 5 拍读一次温度（`TaskTempModule.c:223-226`，每拍 `vTaskDelay(20)`，故实际采样周期约 **120 ms**），然后按下面的 `if / else if` 链裁决：

```
if (bHeatFanSta == true)                                    // :220  ① 总使能
{
    if      ((T > wHeatFanTemp + 50) && (derat == 0))  { Stop(1); }   // :253  G1
    else if ((T > 370)               && (derat == 1))  { Stop(1); }   // :259  G2
    else if ( T > 920 )                                { CloseHeatFan(); } // :265  G3
    else if (wPwm_Old != wPwm) { ...Write(1, wPwm, 50000)... }        // :269  G0 正常输出
}
else { vTaskDelay(500); T = ReadNtcFan(); byTemp[1] = T; }             // :283-288
```

三个保护门的实际作用域：

| 门 | 条件 | 设定 750 时 | 是否置故障码 |
|---|---|---|---|
| G1 | `T > wHeatFanTemp+50` 且 `derat==0` | **80.1℃ 动作**（750+50=800） | **不置**，只 `Stop(1)` |
| G2 | `T > 370` 且 `derat==1` | 37.1℃ 动作（降额模式） | **不置** |
| G3 | `T > 920` | **不可达**（见下） | **不置**（`CloseHeatFan()` 只写 PWM） |

### G3 为什么不可达 —— `[代码]`

G3 是 `else if`，只有在前面的门都为假时才执行。
要让 `T > 920` 成立且 G1 不成立，必须同时满足：

```
T > 920   且   T ≤ wHeatFanTemp + 50
=>  wHeatFanTemp > 870
```

**设定值 ≤ 870 时，92℃ "硬保护"永远不执行。** 设定 750 时它是一段死代码。

### 最关键的推论 —— `[推理]`

上位机显示的"烘干温度"来自 `byTemp[1]`（`TaskTempModule.c:227` 写入，`stOut` 在 xcan 同步区内），而 G1 比较的 `T` 也是 `byTemp[1]`。**两者是同一个变量。**
（此条为结构推断：`byTemp[1]` 由 `FanTempTask` 用 PC4「热风温度接口」写入，语义与"烘干"一致；**待与上位机字段映射表复核**。）

所以：**只要 `bHeatFanSta==1` 且 `wHeatFanTemp==750`，上位机在物理上不可能显示 90℃，因为读数一到 80.1℃ 加热就被切断了。**

反过来说，只要现场真的看到了 90℃，就必然满足 §4 三种情形之一。这不是猜测，是逻辑闭合。

## 4. 到 90℃ 的全部可能路径（穷举，互斥）

| # | 情形 | 机制 | 唯一特征信号（SWD 可区分） |
|---|---|---|---|
| **A** | **设定值被写大** | `wHeatFanTemp ≥ 850`。PID 快照 `stPiPidFan.Temset` 在 `OpenHeatFan()` 时取自该值（`:351`），于是闭环把温度**稳到 90℃ 附近**；同时 G1 阈值升到 950，永不动作，G3 也够不到。**表现就是长期稳定在 89~90℃，不报任何板上故障码。** | `SP_fan ≥ 850` |
| **B** | **保护未使能** | `bHeatFanSta == 0` 时整段保护代码不执行，但 `byTemp[1]` 仍每 500ms 刷新（`:283-288`）。若固化加热（PB15）或外部热源把共用风道烘到 90，烘干通道**完全无保护**。 | `bHeatFanSta == 0` 且 `T_fan` 上升 |
| **C** | **读数瞬时假值** | ADC 并发读/通道错位产生单拍跳变。 | `T_fan` 单拍跳 >5℃ 且下一拍回落 |

**本轮实测已排除 C**（稳态 5 分钟单步最大 0.3℃、无越限）。
**A 与 B 都需要现场复现时抓取**，取值信号已加入值守采样。

### A 的入口只有两处 —— `[代码]`

`wHeatFanTemp` 全工程**只有一个写入点**：

```
TaskMove.c:1038    g_pstC7SysPare->wHeatFanTemp = g_stC7.stIn.wParm[1]*10;
```

外加开机从 Flash 加载（`SysData.c:117`）。两处都**没有任何范围校验**：

- `wParm[1]` 是 `unsigned short`，`wParm[1]*10` 溢出后按 65536 取模。例如上位机误按 0.1℃ 单位下发 7500 → `75000 mod 65536 = 9464` → **946.4℃**。
- `SetTemp()` / `SetFanTemp()` 两个本该做校验的函数**整个函数体被注释掉了**（`TaskTempModule.c:429-451`），是空函数。
- `SysDatainit()` 加载 Flash 参数前**不校验 `byVer` 版本号**（`SysData.c:109-118`），只判断"有没有数据"。换过固件的机器会把旧布局的参数原样读进来，`wHeatTemp`/`wHeatFanTemp` 可能落在别的字段上。

### 为什么"有概率"

A 与 B 都依赖运行时外部条件（上位机某条命令 / 某个流程步骤 / 某次上电），不是每次开机都发生，所以表现为"有概率"。C 已由实测排除。

## 5. "报烘干温度过高"这句话本身就是线索

`clients_cx_cmds.h` 里明确有这两个码：

```
ERR_C7_TEMPHIGH     = 0x0d,   // 制片温度过高
ERR_C7_FANTEMPHIGH  = 0x13,   // 染色后烘干温度过高
```

但全树 grep 的结果是：**这两个码只有定义，没有任何一处 `C7SetErr()` 使用它们**。

也就是说：**固件永远不会上报"烘干温度过高"。** 现场看到的这个故障，是**上位机自己拿 `byTemp[1]` 和阈值比较后生成的**。

这条结论很重要，因为它把排查方向锁死了：
- 板上不会有对应的错误码，翻固件日志/错误码是查不到的；
- 上位机之所以判"过高"，是因为它**确实读到了 ≥90 的数值**；
- 所以要查的是"这个数值怎么来的"，而不是"固件为什么报警"。

### 6.1 H-01：`Write(...,0,...)` 是空操作，加热锁死在旧占空比

**根因（`[代码]`）**

```
pwm.c:129         if(bySpd == 0) return -1;        // 直接返回，输出状态一点没变
pwm.c:138         stRun.blRunning = true;          // 只有非 0 才会走到这里
TaskTempModule.c:171  if(wPwm_Old != wPwm) { Write(0, wPwm*2, 50000); wPwm_Old = wPwm; }
```

`wPwm` 由非零跌到 0 的那一拍：`Write(0, 0, ...)` 返回 -1 什么都没做，
但下一行已经把 `wPwm_Old` 写成 0。此后 `wPwm` 一直为 0，
`if(wPwm_Old != wPwm)` **永远为假**，`Write()` 再也不会被调用。
PWM 通道保持 `bySpd = 上一次的值`、`blRunning = true`，**继续按旧占空比加热**。

**为什么这条比看起来严重**

全工程 `Write(...,0,...)` 共 5 处，我逐处核对过兜底：

| 行号 | 后续是否有 `Stop()` | 结论 |
|---|---|---|
| `:173`（`wPwm*2` 变成 0） | **没有**，下一行是 `//if(wPwm==0) DevPwm->Stop(0);` 被注释 | **唯一的裸口，H-01 的真实入口** |
| `:179`、`:184`、`:412`、`:416`、`:429` | 紧跟 `Stop(0)` / `Stop(1)` | 幂等，无害 |

固化通道的软限幅是 `wTemp1 > wHeatTemp + 50`，设定 68.0℃ 时阈值是 **118℃**；
92℃ 那个分支被 `else if` 排在后面，**设定 ≤87℃ 时永不执行**。
所以锁死后果是：以 1~2% 的占空比持续加热，温度缓慢爬向 118℃ 才被切断。
**这条与"烘干 90 多度"是独立的两件事，但它是一条真实的过温通路，必须修。**

**补丁（`pwm.c`）**

```c
/* AI-FIX H-01：0 速等价于关断，与 Stop() 行为一致 */
if(bySpd == 0)
{
    DevCtr.staChn[dwDev].stRun.bySpd     = 0;
    DevCtr.staChn[dwDev].stRun.blRunning = false;
    *DevCtr.staChn[dwDev].stConfig.pwdPort =
        (unsigned int)(1 - DevCtr.staChn[dwDev].stConfig.byActiveLevel);
    return 0;
}
```

同时把 `blUsing == false` 的检查提到 `bySpd == 0` 之前，语义更严谨（未注册通道一律拒绝）。

### 6.2 H-02：`Write()` 清相位，实际占空比高于设定

**根因（`[代码]`）**

```
pwm.c:135    stRun.bySpdCnt = 0;                    // 每次 Write 都把相位归零
pwm.c:87     if (bySpdCnt == 0) 输出 ON;            // 相位 0 强制 ON
pwm.c:90     else if (bySpdCnt == bySpd) 输出 OFF;
```

周期是 100ms（`KernelProg` 每 1ms 一次、计数到 100 回绕），
而温度环约每 120ms 就可能改写一次占空比。
一次 `Write()` 就把相位打回 0 → 下一拍立刻 ON，
本周期前面已经消耗掉的 OFF 时隙被"退回来"了，等于**白送了一个 ON 时隙**。
改写越频繁，实际占空比偏离设定越大，纹波也越大。

**补丁**

1. 删除 `bySpdCnt = 0`（保留相位，只更新 `bySpd`）
2. `KernelProg` 的比较由 `== bySpd` 改为 **`>= bySpd`**

第 2 点是必须的：保留相位后，若新 `bySpd` 比当前 `bySpdCnt` 小
（例如相位已在 60、设定改成 18），`==` 永远不命中，本周期会**一直 ON 到回绕**。
改成 `>=` 后，该拍立即转 OFF，方向是"少加热"，安全。

已验证 `bySpd == 100` 时 `>=` 不会误触发：`bySpdCnt` 最大到 99，
到 100 之前就被 `if(bySpdCnt == 100)` 重置为 0。

### 6.3 H-04：`bADCbusy` 互斥非原子，且超时后强抢

**根因（`[代码]`）**

```
tempfan.c:88-93   for(i<2000){ if(bADCbusy==false) break; vTaskDelay(1); }
                  bADCbusy = true;                      // ← 无论等没等到，都置位
```

两个独立缺陷：

1. **判断与置位之间可被抢占**：`ReadNtcTem` 与 `ReadNtcFan` 分别跑在两个任务里，
   `if` 判过、还没执行 `break` 时发生任务切换，另一路同样判过 →
   **两路同时认为自己拿到了锁**，共用同一个 ADC1，互相改写 `CHN` 配置。
   轻则主路读到风路的电压，重则两边都读到半配置下的电压。
2. **超时形同虚设**：循环 2000 次（约 2s）后跳出，紧接着**无条件** `bADCbusy = true`，
   等于"等不到也要进"，把互斥彻底废掉。

**补丁（`tempfan.c`，两处 `ReadNtcTem` / `ReadNtcFan` 同改）**

```c
{
    bool blAdcGot = false;

    for(int i = 0; i < 2000; i++)
    {
        taskENTER_CRITICAL();
        if(bADCbusy == false) { bADCbusy = true; blAdcGot = true; }
        taskEXIT_CRITICAL();

        if(blAdcGot == true) break;
        vTaskDelay(1);
    }

    if(blAdcGot == false) return 3000;      /* 取不到锁 → 按传感器故障处理 */
}
```

- 判定+置位进临界区，**原子**。临界区内只有两条赋值，约几个时钟周期，
  对 1kHz 的 PWM 中断无影响。
- 取不到锁**不再强抢**，直接返回哨兵 `3000`（300.0℃），
  走温控环既有的 `wTemp > 900` 停机分支，方向是安全的。
- 原代码在 `bADCbusy = true` 失败路径上不会释放锁 —— 现在失败路径根本没拿锁，
  不存在泄漏；成功路径仍在 `:133` / `:235` 正常释放。

### 6.4 H-05：ADC 三处裸死等，无超时

**根因（`[代码]`）**

```
adc.c:299   while(pstAdc->BitCR2.RSTCAL == 1) {;}     // 复位
adc.c:301   while(pstAdc->BitCR2.CAL    == 1) {;}     // 校准
adc.c:304   while(pstAdc->BitSR.EOC     == 0) {;}     // 转换
adc.c:308   while(pstAdc->BitSR.EOC     == 0) {;}     // 8 次平均，循环内
```

全部是**无上限空转**。只要 ADC 时钟未使能、通道号越界、或 `EOC` 被并发读取清掉，
该任务就**永久停在这行**。而 PWM 的 `dwStep=50000` 保活机制（H-03）会让
加热输出继续按最后的占空比跑 **83 分钟** —— 这构成一条完整的"控制环死亡但加热不停"的通路。

**补丁（`adc.c`）**

新增宏：

```c
#define ADC_WAIT_MAX_LOOP   50000
```

四处等待全部改为有界循环，超时即关 `ADON` 并返回 0：

```c
dwWait = 0;
while(pstAdc->BitSR.EOC == 0)
{
    if(++dwWait > ADC_WAIT_MAX_LOOP) { pstAdc->BitCR2.ADON = 0; return 0; }
}
```

另加一处防御：`if(dwDoTims == 0) dwDoTims = 1;`（原实现末尾 `dwTmp /= dwDoTims`，传 0 会除零）。

**超时上限的取值依据**：一次完整转换 = (239.5 + 12.5) 周期 @14MHz ≈ 18µs，
校准约 6µs；50000 次空转按 72MHz、每次 6~10 个时钟算约 5~7ms，
**余量超过 250 倍**，正常时序下永远不会触发，只把"永久死等"降级为"故障返回"。

**返回 0 为什么是安全的**：`tempfan.c` 取三次中值后，
`wAdcMid <= OPEN_VALUE(10)` 会判为传感器开路，转成 3000 哨兵 → 停机。
方向与硬件故障一致，不会造成"读 0 就按 0℃ 加热"。

### 6.5 H-06：热保护环跑在最低调度等级

**根因（`[代码]`）**

```
TaskTempModule.c:367  xTaskCreate(TempModuleTask, ..., tskIDLE_PRIORITY, NULL);   // 0
TaskTempModule.c:378  xTaskCreate(FanTempTask,    ..., tskIDLE_PRIORITY, NULL);   // 0
```

`configMAX_PRIORITIES = 5`（合法 0~4）、`configUSE_PREEMPTION = 1`。
全机 11 个任务里 10 个都是 0，只有 `XcanTask` 是 1。
温度控制与**全部过温保护判断**都在这个最低池里，与 9 个业务任务做时间片轮转，
重负载时可能被连续推迟多个 tick。

**补丁**

两处均改为优先级 **2**：

```c
xTaskCreate( TempModuleTask, (char const*)"TempModuleTask", 256, NULL, 2, NULL);
xTaskCreate( FanTempTask,    (char const*)"FanTempTask",    256, NULL, 2, NULL);
```

**为什么选 2 而不是 4**：热保护应当优先于通信，但不宜压制到极限。
取 2（高于 `XcanTask` 的 1）即可脱离最低池，且本任务每拍末尾都有 `vTaskDelay(20)`，
绝大部分时间处于阻塞态，不会饿死低优先级任务；
单次占用 CPU 约 100~200µs（ADC 里的 `vTaskDelay(1)` 期间主动让出），
对 5ms 的 xcan 同步周期无实质影响。
**若现场发现通信异常，改回 1 即可**，不影响本补丁其他部分。

## 7. 为什么"过冲"这条路走不通（定量）

若真过冲，需要"温度到 75℃ 时功率仍在高位，余热把温度顶上去"。实际控制律给出的余量是：

到 75.0℃ 时 `wPwm = 10%`，而维持 75℃ 需要 18% → **净功率已经是负的**，闭环在 75.2℃ 就把占空比压到 0。
过冲量上限 ≈ 升温速率 × 传感器时间常数。要在 75℃ 设定下冲出 15℃，需要 NTC 时间常数约 35 秒——风道内小体积 NTC 通常是 5~15 秒，量级差了一倍以上。

**所以过冲最多把温度顶到 78~82℃，正好落在 G1 的 80.1℃，到不了 90。** 这也解释了为什么之前仿真里标称参数峰值只有 75.0℃。

**结论：90℃ 不是"控不住"，是"目标被改了"或"保护没开着"。**

## 8. 现场判定流程（纯只读，5 分钟定位）

复现时（或复现后立即）用 SWD 读这 4 个地址：

| 地址 | 含义 | 读法 |
|---|---|---|
| `0x20005788` | `byTemp[0]` 低 16 位、`byTemp[1]` 高 16 位（0.1℃） | `Mem32 0x20005788, 1` |
| `0x20000228` | `g_pstC7SysPare` 指针 | 取其值 |
| `ptr + 0x2A` | **`wHeatFanTemp` 烘干设定** | `Mem32 <ptr+0x28>, 1`，高 16 位 |
| `0x20006AB8` | 字节1=`bHeatSta`，字节2=`bHeatFanSta` | `Mem32 0x20006AB8, 1` |

判读表：

| `wHeatFanTemp` | `bHeatFanSta` | 判定 | 处理方向 |
|---|---|---|---|
| **≥850** | 1 | **情形 A：设定值被写大** | 查上位机哪条命令写了它（`C7_D_SETFANTEMP` / 开机参数）；确认下发单位是 ℃ 还是 0.1℃ |
| =750 | **0** | **情形 B：保护未使能** | 查谁调了 `CloseHeatFan()`/`CloseFunHeat()`；排查固化加热是否在烘同一风道 |
| =750 | 1 | 读数对不上 → 硬件/传感器 | 独立温度计对比 NTC 实际位置温度；查 H-07 无风加热 |
| ≥9000 | 任意 | `wParm[1]*10` 溢出 | `TaskMove.c:1038` 溢出缺陷 |
